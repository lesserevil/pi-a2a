# Migration design document: pi-a2a → Google A2A (Agent2Agent) open protocol

> Status: **confirmed (decisions locked)** — implement along these lines.
> Specification: A2A Protocol v1.0.0 (https://a2aproject.github.io/A2A/v1.0.0/specification/, normative: `spec/a2a.proto`).
> Goal: replace the current custom wire protocol with A2A's **JSON-RPC 2.0 over HTTP** transport while preserving the pi experience (LAN-only, zero-config discovery, delegation-injection loop, Node+Bun dual runtime, `bonjour-service` as the only dependency).

---

## 0. The four confirmed key decisions

| # | Decision | Outcome |
|---|------|------|
| DP0 | Protocol binding | **JSON-RPC** (spec §9). Single endpoint `POST /rpc`, PascalCase method names (`SendMessage`/`GetTask`). |
| DP2 | Data model | **Everything goes through the Task model**: every `SendMessage` returns a `Task` (uniform wire format). Behaviour is still governed by `metadata.kind` for injection policy. |
| DP3 | Result return | **push-notification (webhook)**, zero latency, semantically closest to the status quo (inbound push). `GetTask` is kept as a fallback (in case a webhook is lost). |
| DP7 | Compatibility | **Hard cut**: A2A v1.0 only; legacy proto=1 is not supported. |

The rest (DP1 keep mDNS discovery, DP4 shared secret as Bearer, DP5 five tool signatures unchanged, DP6 keep the injection loop, DP8 keep the JSON store) follow the draft conclusions.

---

## 1. One-line summary

**Every pi agent is both an "A2A Server" and an "A2A Client"**:
- **Server**: runs HTTP locally, exposing `/.well-known/agent-card.json` + `POST /rpc` (JSON-RPC: `SendMessage` / `GetTask`) + `POST /a2a/notify` (push-notification webhook receiver).
- **Client**: when sending a message or delegating, acts as a client calling the peer server's JSON-RPC methods.
- Symmetry comes for free (both sides run a server and can act as a client). The discovery layer (mDNS + presence) maps peerName → A2A endpoint URL.

## 2. Data-model mapping (all-Task model)

### 2.1 Current `Message` fields → A2A targets

| Current field | A2A target | Notes |
|---|---|---|
| `id` | `Message.messageId` | generated by the creator |
| `thread_id` | `Task.contextId` | same thread = same contextId (shared by multiple tasks) |
| `reply_to` | contextId continuation / `referenceTaskIds` | A2A continues threads via contextId |
| `from_id`/`from_name` | Agent Card `name` + Bearer identity | from_name comes from the peer's Card/mDNS |
| `to_name` | peer server endpoint URL (resolved via mDNS/presence) | not a wire field; means "which server to call" |
| `subject` | `Message.metadata.subject` | A2A Message has no native subject |
| `body` | `Part{ text: body }` (a single TextPart) | the parts array holds one TextPart |
| `kind` | `Message.metadata.kind` ∈ {message,request,result} | **the server uses this to decide injection + whether to register a push** |
| `direction` | local view only, not on the wire | kept in the store |
| `created_at` | `TaskStatus.timestamp` (ISO 8601 UTC) | A2A requires ISO 8601 |

### 2.2 `kind` × Task behaviour matrix (core)

Every `SendMessage` returns a Task, but its lifecycle is determined by `metadata.kind`:

| `kind` | after the server creates the task | Inject into recipient's session? | Register push (return to sender)? | Sender waits for result? |
|---|---|---|---|---|
| **`message`** (chat) | immediately **COMPLETED** (stored in inbox + toast; the task serves as a delivery record) | ❌ | ❌ | ❌ (returns on the synchronous ack) |
| **`request`** (delegation) | **WORKING** (stored in inbox + injected for the agent to handle) | ✅ | ✅ (the sender registers a webhook) | ✅ (waits for the pushed result) |
| **`result`** (result delivery) | immediately **COMPLETED** (stored in inbox + injected = auto-received) | ✅ | ❌ | ❌ |

> **Key point**: the all-Task model unifies the wire form (the response is always `{task}`), but the UX split remains: only `request` interrupts and waits, `result` is auto-received, and `message` merely notifies. push-notification is registered only for `request` (only the sender needs to wait for a result), so the all-Task model adds no latency or noise to chat.

### 2.3 Result return (request → result) under the push model

Current behaviour: BE finishes processing → actively pushes the result to FE.
A2A push model: BE is the **server** for the original request (BE holds the task). "Returning the result" means BE sets the task to COMPLETED + attaches an Artifact, then **POSTs a push-notification to the webhook FE registered in the request** → FE receives → injects. Zero latency, semantically identical to the current inbound push.

> The loop (FE sends request → BE handles automatically → BE returns result → FE auto-receives the injection) is **fully preserved**, with latency equal to the status quo (immediate push).

## 3. Sequence diagrams

### 3.1 Chat message (kind=message) — synchronous ack, no push

```
FE (client)                              BE (server)
  POST /rpc SendMessage                    │
    message.metadata.kind="message"        │
    message.parts=[{text:body}]  ────────► │  validate Bearer
                                           │  create Task(COMPLETED)  ← terminal immediately
                                           │  store inbox + inboundTask
                                           │  toast("📨 ...")   ← notify only, no injection
  {result:{ task:{ id, status:COMPLETED}}}◄│  return COMPLETED task (no push registered)
tool returns "✅ sent to BE"
```

### 3.2 Delegation loop (kind=request → result, pushed back) ★core

```
FE (client)                BE (server)                 FE webhook (/a2a/notify)
  POST /rpc SendMessage       │
    metadata.kind="request"   │
    configuration.             │
      pushNotificationConfig:{ │
        url:"http://FE:port/a2a/notify",
        token:<secret>,        │
        authentication:{schemes:["Bearer"]} }
    parts=[{text:request body}]  ─►│  create Task(SUBMITTED→WORKING)
                              │  inboundTask.taskId + store pushConfig
                              │  store inbox
                              │  ★ pi.sendUserMessage(inject request) ──► BE LLM processes immediately
  {result:{ task:{id,WORKING}}}◄│
                              │
tool returns "✅ delegated, task=XXX" │  ...BE processing... (task=WORKING)
store.outboundTask[taskId]    │
  = {peer:BE, awaitPush:true} │  BE LLM finishes → a2a_reply(msgId, result)
                              │  → look up inboundTask[msgId]
                              │  → set Task COMPLETED + Artifact{parts:[{text:result}]}
                              │  → store sent(kind=result)
                              │
                              │  POST /a2a/notify       │
                              │   Authorization: Bearer │
                              │   X-A2A-Notification-Token
                              │   body:{ task:{ id,     │
                              │     status:COMPLETED,   │
                              │     artifacts:[{parts:[{text:result}]}] } }
                              │  ─────────────────────► │  FE validates token
                              │                         │  ← look up outboundTask[task.id]
                              │                         │  extract Artifact text
                              │                         │  build local inbox(result)
                              │  ◄── 200 OK             │  ★ inject into FE session
                              │                         │  remove outboundTask
                              │  ◄──────────────────────│  (FE needs no manual a2a_read)
```

### 3.3 The two branches of a2a_reply

```
Branch A: the original message is a request I received (I am the server, holding the task with pushConfig stored)
  → set Task COMPLETED + Artifact(body)
  → POST to the peer's webhook per pushConfig (the peer auto-receives the injection)
  → no need to send a new SendMessage

Branch B: the original message was a message / was sent by me (no task on my side)
  → I act as client and SendMessage to the peer server
  → metadata.kind = (was it a request ? result : message)
  → the peer handles it per the §2.2 matrix
```

### 3.4 Fallback: GetTask to prevent loss

Webhooks are at-least-once and can be lost (FE restart / network flakiness). FE keeps `outboundTasks` (awaitPush). A low-frequency fallback sweep (every 15s by default) actively calls `GetTask` for tasks that **have received no push for over 30s**: if already COMPLETED it injects and removes them, preventing permanent loss of results. The normal path never calls GetTask, so there is no extra traffic.

## 4. Planned changes per file

### 4.1 `extensions/net.ts` (rewrite)

The `Network` class has three areas of responsibility:

**A2A server side** (`node:http` routes):
- `GET /.well-known/agent-card.json` → Agent Card (§5).
- `GET /health` → kept (mDNS keep-alive probe; not in spec, harmless).
- `POST /rpc` → JSON-RPC dispatch:
  - `SendMessage`: validate Bearer → read `metadata.kind` + `configuration.pushNotificationConfig` → create Task (state + injection + pushConfig per §2.2) → return `{task}`.
  - `GetTask`: validate Bearer → return local task state (for the fallback).
  - unknown method → `-32601`.
  - errors use the spec §5.4 A2A error codes (e.g. `-32001` TaskNotFound) + `google.rpc.ErrorInfo` data.
- `POST /a2a/notify` → **push-notification receiver**: validate the token → parse `{task:{id,status,artifacts}}` → look up `outboundTasks` → if terminal, build a local inbox(result) + inject + remove → 200.

**A2A client side** (`fetch`):
- `send(peer, msg, cfg?)` → JSON-RPC `SendMessage`, POST `peer/rpc`, returns a Task.
- `getTask(peer, taskId)` → `GetTask`, returns a Task (fallback).
- `getAgentCard(peer)` → GET `peer/.well-known/agent-card.json` (cached after discovery; validates protocolVersion).
- `notifyPeer(peerEndpoint, token, task)` → when BE completes a task, POSTs a push to the peer's webhook.

**Discovery layer** (largely unchanged):
- mDNS TXT: `proto` changes from `"1"` to `"a2a"`, plus a new `a2aver=1.0`.
- presence files likewise.
- `onPeerUp` fetches the Agent Card once in the background (hard cut: ignore the peer if protocolVersion is not 1.0).

**Push waiting + fallback**:
- `outboundTasks` (in the store) records tasks awaiting a push.
- Fallback scanner (15s default): calls `getTask` for tasks with no push for >30s.
- Offline outbox kept: when the peer is offline, a failed `send` is queued in the outbox and redelivered on reconnect (same semantics as now).

### 4.2 `extensions/index.ts` (adapt, signatures unchanged)

- `startEngine` Network hooks:
  - `onMessageReceived` (notification + injection for message/result) is nearly unchanged.
  - add `onTaskReceived` (injection for requests) — extract the existing request branch.
- The 5 tools' `execute` bodies switch to A2A:
  - `a2a_send`: build an A2A Message (subject→metadata, body→TextPart, kind→metadata); for `request` additionally attach `pushNotificationConfig` (url = own /a2a/notify, token = workspaceSecret) and store the returned taskId in `outboundTasks`.
  - `a2a_reply`: branch per §3.3 — if a local task exists, `completeInboundTask` + `notifyPeer`; otherwise `send`.
  - `a2a_inbox`/`a2a_read`/`a2a_peers`: **unchanged** (they read the local store / peer table).

### 4.3 `extensions/store.ts` (small extension)

- `Message` gains optional fields: `taskId?`, `contextId?`, `taskState?`.
- two new collections (persisted):
  - `inboundTasks: { taskId, msgId, contextId, state, fromName, createdAt, artifactText?, pushConfig?:{url,token} }[]`
  - `outboundTasks: { taskId, msgId, contextId, peerName, peerEndpoint, createdAt, awaitPush, lastPushAt? }[]`
- new methods: `addInboundTask / getInboundTask(taskId|msgId) / completeInboundTask(taskId, artifactText) / addOutboundTask / resolveOutboundTask(taskId) / getStaleOutbound(olderThanMs)`.
- everything else unchanged.

### 4.4 `extensions/config.ts` + `config.example.json`

`A2aConfig` additions (all optional, with defaults):
- `rpcPath?` (default `/rpc`), `agentCardPath?` (default `/.well-known/agent-card.json`)
- `notifyPath?` (default `/a2a/notify`)
- `pushBackstopMs?` (default 30000), `pushSweepMs?` (default 15000)
- all other fields unchanged.

### 4.5 `README.md` / `SKILL.md`

Redraw the architecture diagram (A2A JSON-RPC + Agent Card + push webhook). Replace the HTTP endpoint table with an A2A method table. Add a "Task behaviour" column to the message-type table. Document that results now come back immediately via push.

### 4.6 `scripts/be-daemon.ts`

Reuse the new `Network`. On `request` → create a task → immediately `completeInboundTask` + `notifyPeer` (a canned reply pushed back to FE). Heartbeat/exit unchanged.

## 5. Agent Card (returned by the server)

```jsonc
GET /.well-known/agent-card.json  →  200 application/json
{
  "name": "backend",                       // peerName
  "description": "writes the API",         // role
  "version": "1.0.0",
  "supportedInterfaces": [
    { "url": "http://<host>:<port>/rpc", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" }
  ],
  "capabilities": { "streaming": false, "pushNotifications": true, "extendedAgentCard": false },
  "securitySchemes": {
    "ws": { "httpAuthSecurityScheme": { "scheme": "Bearer", "description": "shared workspace secret" } }
  },
  "securityRequirements": [ { "ws": [] } ],
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [
    { "id": "pi-a2a", "name": "backend", "description": "writes the API", "tags": ["pi","agent","a2a"] }
  ]
}
```

> Workspace isolation is still enforced by the shared secret during Bearer validation; the Card does not expose the workspace.

## 6. JSON-RPC wire examples

**SendMessage (delegation, with push config):**
```jsonc
POST /rpc   Authorization: Bearer <secret>   Content-Type: application/json
{ "jsonrpc":"2.0", "id":1, "method":"SendMessage",
  "params": {
    "message": { "messageId":"msg_abc", "role":"ROLE_USER", "contextId":"ctx_fe1",
      "parts":[{"text":"<request body>"}],
      "metadata": { "kind":"request", "subject":"login endpoint signature", "from":"FE" } },
    "configuration": {
      "pushNotificationConfig": {
        "url": "http://192.168.1.5:54321/a2a/notify",
        "token": "<workspaceSecret>",
        "authentication": { "schemes": ["Bearer"] }
      }
    }
  } }
```
**Response (task WORKING):**
```jsonc
{ "jsonrpc":"2.0", "id":1,
  "result": { "task": { "id":"task_007", "contextId":"ctx_be1",
    "status": { "state":"TASK_STATE_WORKING", "timestamp":"2026-06-19T10:00:00.000Z" } } } }
```

**push-notification (POSTed to FE's webhook after BE completes):**
```jsonc
POST /a2a/notify   Authorization: Bearer <secret>   X-A2A-Notification-Token: <secret>
{ "task": { "id":"task_007", "contextId":"ctx_be1",
    "status": { "state":"TASK_STATE_COMPLETED", "timestamp":"..." },
    "artifacts": [ { "artifactId":"art_1", "parts":[{"text":"<result body>"}] } ] } }
```
→ FE validates the token → looks up outboundTasks[task_007] → injects → `200 OK`.

**GetTask (fallback):**
```jsonc
POST /rpc   { "jsonrpc":"2.0", "id":2, "method":"GetTask", "params": { "id":"task_007" } }
```

**Error:**
```jsonc
{ "jsonrpc":"2.0", "id":2,
  "error": { "code":-32001, "message":"Task not found",
    "data":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo","reason":"TASK_NOT_FOUND","domain":"a2a-protocol.org"}] } }
```

> v1.0 method names are PascalCase. Legacy v0.3 `message/send` is not supported (hard cut).

## 7. Constraint checklist

| Constraint | Met |
|---|---|
| Minimal dependencies (bonjour-service only) | A2A is pure JSON-RPC, hand-written on `node:http` + global `fetch`, **no SDK introduced**. |
| Node + Bun dual runtime | `createRequire` loads bonjour-service; `fetch`/`node:http` are supported by both runtimes. |
| LAN-only (`0.0.0.0`, no hardening) | Preserved. The push-notification webhook uses in-LAN peer addresses and exposes nothing publicly. |
| Does not break the delegation-injection loop | The §3.2 sequence shows the loop is preserved; results return immediately via push, latency ≈ status quo. |

---

## 8. Risks and trade-offs

1. **R1 push loss**: webhooks are at-least-once and can be lost (FE restart/flakiness). Covered by the §3.4 fallback sweep (GetTask after >30s without a push). No extra traffic on the normal path.
2. **R2 metadata.kind extension**: using metadata to let the server decide injection is a legal extension but deviates from "an A2A server must process every message". It only affects pi-a2a↔pi-a2a; toward third-party A2A agents it degrades to "treat everything as a request".
3. **R3 single JSON-RPC binding**: interoperability is only guaranteed between pi-a2a instances; the Agent Card declares the binding truthfully, and adding REST later is additive.
4. **R4 hard cut**: legacy proto=1 peers silently stop working (ignored by the discovery layer). Teams must upgrade together.
